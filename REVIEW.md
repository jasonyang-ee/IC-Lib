## Binding behavior to preserve

`_a`, `_b`, and `_c` are separate footprint bases; each base groups its `.psm`/`.bsm`/`.dra` companions. Automatic learning requires exactly one footprint base and no more than one pad/model of each type. Multiple variants or multiple unbound pads are intentionally ambiguous: co-presence does not establish which pad belongs to which footprint. Explicit File Library bindings support multiple pads. Review must not fabricate these mappings or remove unrelated unbound files.

## Round 3 coverage and fixes

Round 3 starts at `b8ef890` on `main` with a clean worktree. It continues the highest-impact unfinished CAD section; the queued non-CAD areas above are still unexamined. No delegation or live data writes.

- R3-1 (high, fixed; closes legacy R2-6 paths): `finalizeTempFile` and `restoreDeletedFile` now share `cadUploadService`. Target component ID or legacy MPN lookup locks current rows, rejects ambiguous/missing identities, and enforces the existing ECO edit policy before publication. Registration, junction insertion and TEXT regeneration share the transaction. New-part/ECO staging omits live identity; direct edits use the selected ID even if the MPN changes. Overwrite is rejected whenever ECO is enabled, including requests without a component and admin requests; this preserves the existing no-live-overwrite invariant. The conflict modal disables both overwrite controls.
- R3-2 (high, fixed; legacy rename portion of R2-6/R2-8): `renameFile` passes the authenticated actor into `renameCadFile`; the service locks the file and all current consumers before policy evaluation and mutation. A new-status supplied MPN cannot authorize changes to a shared file used by a controlled part. Admin direct rename remains allowed. Non-admin ECO-mode legacy renaming of untracked files requires scan first because consumer policy cannot be established from an absent CAD row. Staged temp renames stay available. File Library shared-ECO creation semantics are unchanged and require the remaining review below.
- R3-3 (medium, fixed; R2-7): finalization preserves an unresolved collision instead of discarding it. New targets use exclusive copying while retaining the temp token; overwrite backs up the old bytes and replaces without deleting the target first. Publication/link failure rolls back DB writes and restores disk state before releasing the transaction; incomplete physical recovery is reported explicitly. Temp cleanup occurs only after successful commit. Per-destination advisory locks serialize these finalization/restore requests, and registration holds the tracked row during publication.
- R3-4 (medium, fixed; R2-7 client side): direct/add/ECO Library save consumes per-token results. Partial success removes only successful tokens, stops the component/ECO save, and displays the failed filenames. Retry sends only remaining uploads; cancel only cleans those tokens. New-part finalization no longer risks linking by an MPN that belongs to another existing component. Each file is still a separate committed operation; this does not make an entire multi-file/component save atomic.
